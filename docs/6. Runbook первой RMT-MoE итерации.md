# Runbook первой RMT-MoE итерации

## Назначение

Первая итерация проверяет one-layer гипотезу H1 на реальных activation traces:

`dataset -> traces -> functional sketches -> finite-size RMT diagnostics -> candidate plans -> reversible merge/prune -> validation selection -> test evaluation`.

Она не проверяет multi-layer compression, dynamic-k, router bias или distributed communication.

## Что считается experiment-ready

Запуск является научным, а не только техническим, если одновременно выполняются условия:

1. `calibration.source` равен `hf_dataset` или указывает на заранее собранный реальный artifact.
2. Calibration, validation и test являются непересекающимися наборами.
3. RMT diagnostics содержат `r_detect`, `r_stable`, `r_useful`, empirical null edge и principal-angle stability.
4. Candidate model реально применяется к одному MoE-слою и восстанавливается после оценки.
5. Baseline и candidates используют одни и те же token batches и profiler settings.
6. Test используется только для кандидатов, выбранных по validation.
7. Каждый завершённый candidate сохраняется в JSONL до запуска следующего.

## Архитектурный контракт Qwen1.5-MoE

До сбора traces runtime обязан подтвердить следующую семантику:

- `routed_experts=60` — эксперты, между которыми выбирает sparse router;
- `routed_top_k=4` — число routed experts на токен;
- `shared_experts=4` — эквивалентная ширина always-active shared-ветки;
- shared expert и `shared_expert_gate` не входят в candidate groups и не изменяются one-layer transform.

Число восемь здесь означает суммарно четыре routed и четыре shared пути, но не является значением `runtime.top_k`. Эти значения записываются в runtime contract и metadata каждого trace artifact. Несовпадение с загруженной моделью завершает запуск ошибкой `runtime_architecture_mismatch`.

## Окружение

Не переустанавливать рабочую CUDA-сборку Torch. Установить только experiment dependencies:

```bash
python -m pip install -r requirements-experiment.txt
```

Проверить runtime:

```bash
python -m moe_opt_runner.preflight \
  --config configs/experiments/h1_rmt_one_layer_pilot.json \
  --require-cuda \
  --check-model-config
```

Запускать эксперимент можно только при `"ready": true`.

## Запуск

Не запускать первую серверную итерацию одной командой `moe_opt_runner.main`. Для неё используется resumable runner: один процесс выполняет ровно один ограниченный шаг и завершается.

```bash
python -m pytest -q
export CONFIG=configs/experiments/h1_rmt_one_layer_pilot.json

# 1. Только calibration traces и H1 diagnostics.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_calibration
# 2. Validation data и baseline.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_validation
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step h1_diagnostics
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step baseline_validation

# 3. Один validation batch: не более двух кандидатов и 20 минут после загрузки модели.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" \
  --step validate_candidates --max-items 2 --max-step-seconds 1200

# Проверить remaining_items. Повторять предыдущую команду вручную до remaining_items=0.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step status

# 4. Зафиксировать selection до любого обращения к test split.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step select_candidates

# 5. Test artifacts, baseline и ограниченные batches выбранных кандидатов.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_test
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step baseline_test
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" \
  --step test_selected --max-items 2 --max-step-seconds 1200

# Повторять test_selected вручную до remaining_items=0, затем собрать отчёт.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step build_summary
```

Код возврата `124` от `timeout` означает, что текущий процесс остановлен по внешнему лимиту. Повторный запуск того же шага безопасен: успешно завершённые candidates читаются из `pilot_runs.jsonl` и пропускаются. Не оборачивать candidate-команды в бесконечный `while`; каждый следующий batch запускается только после просмотра `status` и GPU memory.

Не запускать два процесса `validate_candidates` или `test_selected` параллельно: JSONL-ledger рассчитан на одного writer. Для изменения сетки, seed, лимитов данных или model config использовать новый `artifacts.root_dir`, а не продолжать старый state.

## Первая сетка

- модель: `Qwen/Qwen1.5-MoE-A2.7B-Chat`;
- слой: `0` как инженерный smoke; после него выбрать один ранний, средний и поздний слой;
- методы: `random_merge`, `usage_prune`, `functional_cosine`, `rmt_geometry`;
- compression fractions: `0.10`, `0.25`, `0.40`;
- quality budgets: `0.01`, `0.03`, `0.05` relative perplexity degradation;
- три seed для random baseline;
- RMT и deterministic baselines запускаются один раз на configuration point.

## Артефакты

В `artifacts/h1_rmt_one_layer_pilot_resumable` формируются:

- `traces/trace_manifest.json`;
- `h1_diag_0.json` и `h1_diag_0.pt`;
- `pairs_0.pt`;
- `pilot_runs.jsonl` с baseline, completed и failed candidates;
- `pilot_state.json` с завершёнными шагами, candidate IDs и `remaining_items`;
- `pilot_selection.json` с immutable selection после validation;
- `pilot_summary.json`;
- `artifacts_manifest.json` и `run_summary.json`.

`pilot_runs.jsonl` является первичным журналом. `pilot_summary.json` является производным отчётом.

## Интерпретация первой итерации

Главная диаграмма строится по трём осям:

- relative perplexity degradation;
- active model parameter memory reduction;
- measured tokens per second.

`peak_memory_mb` внутри reversible session является диагностикой процесса, но не доказательством memory reduction: исходные параметры удерживаются rollback snapshot. Физическое снижение peak memory подтверждается позднее загрузкой отдельного materialized checkpoint.

RMT-кандидат считается перспективным, если:

1. проходит хотя бы quality budget `3%` на validation и test;
2. не хуже random/functional-cosine при одинаковой compression fraction;
3. имеет воспроизводимые `r_stable/r_useful` и principal angles;
4. даёт положительное снижение active parameter memory;
5. не демонстрирует систематического падения throughput.

## Следующий gate

После успешной one-layer итерации запускаются три representative layers. Только после подтверждения воспроизводимости добавляются:

1. materialized checkpoint reload для честного peak-memory профиля;
2. multi-layer controller `keep/prune/merge/abstain`;
3. H2 router bias;
4. H3 dynamic-k;
5. communication-aware profiling.
