# Порядок запуска первой RMT-MoE итерации

## Назначение

Первая итерация проверяет однослойную гипотезу H1 на реальных трассах
активаций:

`датасет -> трассы -> функциональные эскизы -> конечномерная RMT-диагностика -> планы кандидатов -> обратимые merge/prune -> отбор на проверочной выборке -> оценка на контрольной выборке`.

Она не проверяет многослойное сжатие, динамический выбор `k`, смещение
маршрутизатора или распределенный обмен данными.

## Готовность эксперимента

Запуск является научным, а не только техническим, если одновременно выполняются условия:

1. `calibration.source` равен `hf_dataset` или указывает на заранее собранный
   реальный артефакт.
2. Калибровочная, проверочная и контрольная выборки не пересекаются.
3. RMT-диагностика содержит `r_detect`, `r_stable`, `r_useful`, эмпирическую
   границу нулевой модели и оценку устойчивости главных углов.
4. Модель-кандидат действительно применяется к одному MoE-слою и
   восстанавливается после оценки.
5. Базовая модель и кандидаты используют одинаковые пакеты токенов и настройки
   профилировщика.
6. Контрольная выборка используется только для кандидатов, выбранных по
   проверочной выборке.
7. Каждый завершенный кандидат сохраняется в JSONL до запуска следующего.

## Архитектурный контракт Qwen1.5-MoE

До сбора трасс среда исполнения должна подтвердить следующую семантику:

- `routed_experts=60` — эксперты, между которыми выбирает разреженный
  маршрутизатор;
- `routed_top_k=4` — число маршрутизируемых экспертов на токен;
- `shared_experts=4` — эквивалентная ширина постоянно активной общей ветви;
- общий эксперт и `shared_expert_gate` не входят в группы кандидатов и не
  изменяются однослойным преобразованием.

Число восемь здесь означает суммарно четыре маршрутизируемых и четыре общих
пути, но не является значением `runtime.top_k`. Эти значения записываются в
контракт среды исполнения и метаданные каждого артефакта трассировки.
Несовпадение с загруженной моделью завершает запуск ошибкой
`runtime_architecture_mismatch`.

## Окружение

Не переустанавливать рабочую CUDA-сборку Torch. Установить только зависимости
эксперимента:

```bash
python -m pip install -r requirements-experiment.txt
```

Проверить среду исполнения:

```bash
python -m moe_opt_runner.preflight \
  --config configs/experiments/h1_rmt_one_layer_pilot.json \
  --require-cuda \
  --check-model-config
```

Запускать эксперимент можно только при `"ready": true`.

## Запуск

Не запускать первую серверную итерацию одной командой `moe_opt_runner.main`.
Для нее используется возобновляемый исполнитель: один процесс выполняет ровно
один ограниченный шаг и завершается.

```bash
python -m pytest -q
export CONFIG=configs/experiments/h1_rmt_one_layer_pilot.json

# 1. Только калибровочные трассы и H1-диагностика.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_calibration
# 2. Проверочные данные и базовая оценка.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_validation
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step h1_diagnostics
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step baseline_validation

# 3. Один пакет проверочных запусков: не более двух кандидатов и 20 минут после загрузки модели.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" \
  --step validate_candidates --max-items 2 --max-step-seconds 1200

# Проверить remaining_items. Повторять предыдущую команду вручную до remaining_items=0.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step status

# 4. Зафиксировать результат отбора до любого обращения к контрольной выборке.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step select_candidates

# 5. Контрольные артефакты, базовая оценка и ограниченные пакеты выбранных кандидатов.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step traces_test
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step baseline_test
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" \
  --step test_selected --max-items 2 --max-step-seconds 1200

# Повторять test_selected вручную до remaining_items=0, затем собрать отчёт.
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step build_summary
```

Код возврата `124` от `timeout` означает, что текущий процесс остановлен по
внешнему ограничению. Повторный запуск того же шага безопасен: успешно
завершенные кандидаты читаются из `pilot_runs.jsonl` и пропускаются. Не
оборачивать команды запуска кандидатов в бесконечный `while`; каждый следующий
пакет запускается только после просмотра `status` и памяти GPU.

Не запускать два процесса `validate_candidates` или `test_selected`
параллельно: журнал JSONL рассчитан на один записывающий процесс. При изменении
сетки, начальных значений генератора, ограничений данных или конфигурации модели
следует использовать новый `artifacts.root_dir`, а не продолжать прежнее
состояние.

## Первая сетка

- модель: `Qwen/Qwen1.5-MoE-A2.7B-Chat`;
- слой: `0` для инженерной проверки; после него выбрать один ранний, средний и
  поздний слой;
- методы: `random_merge`, `usage_prune`, `functional_cosine`, `rmt_geometry`;
- доли сжатия: `0.10`, `0.25`, `0.40`;
- допустимая относительная деградация perplexity: `0.01`, `0.03`, `0.05`;
- три начальных значения генератора для `random_merge`;
- RMT и детерминированные базовые методы запускаются один раз в каждой точке
  конфигурации.

## Артефакты

В `artifacts/h1_rmt_one_layer_pilot_resumable` формируются:

- `traces/trace_manifest.json`;
- `h1_diag_0.json` и `h1_diag_0.pt`;
- `pairs_0.pt`;
- `pilot_runs.jsonl` с базовой оценкой, завершенными и неуспешными кандидатами;
- `pilot_state.json` с завершенными шагами, идентификаторами кандидатов и
  `remaining_items`;
- `pilot_selection.json` с неизменяемым результатом отбора на проверочной
  выборке;
- `pilot_summary.json`;
- `artifacts_manifest.json` и `run_summary.json`.

`pilot_runs.jsonl` является первичным журналом. `pilot_summary.json` является производным отчётом.

## Интерпретация первой итерации

Главная диаграмма строится по трём осям:

- относительная деградация perplexity;
- снижение памяти активных параметров модели;
- измеренная пропускная способность в токенах в секунду.

`peak_memory_mb` внутри обратимого сеанса является диагностикой процесса, но не
доказательством снижения памяти: исходные параметры удерживаются снимком для
отката. Физическое снижение пикового потребления памяти позднее подтверждается
загрузкой отдельной материализованной контрольной точки.

RMT-кандидат считается перспективным, если:

1. укладывается в допустимую деградацию `3%` на проверочной и контрольной
   выборках;
2. не хуже `random_merge` и `functional_cosine` при одинаковой доле сжатия;
3. имеет воспроизводимые `r_stable`, `r_useful` и главные углы;
4. уменьшает память активных параметров;
5. не демонстрирует систематического падения пропускной способности.

## Абляция выбора пар и спектрального ранга

После пилота с отложенной контрольной выборкой используется конфигурация
`configs/experiments/h1_rmt_pairing_rank_ablation_one_layer_pilot.json`.
Она переиспользует калибровочные, проверочные и контрольные трассы, а также
H1-представление из
`artifacts/h1_rmt_hybrid_heldout_one_layer_pilot` только для чтения, но пишет
новый журнал и сводку в отдельный `artifacts.root_dir`.

Сетка содержит 30 кандидатов для проверочной выборки:

- `usage_prune` и `usage_guided_merge` по одному разу на долю сжатия;
- `rmt_geometry` и `rmt_functional_usage` для рангов `1`, `4`, `8`, `18`;
- три доли сжатия `0.10`, `0.25`, `0.40`.

`usage_guided_merge` выбирает столько же малоиспользуемых экспертов, сколько
удаляет `usage_prune`, но объединяет каждый из них с уникальным функционально
похожим экспертом из сохраняемой части. Это отделяет качество выбора экспертов
от различия операций `prune` и `merge`.

Ранги `4`, `8` и `18` являются исследовательской абляцией. Они не заменяют
оценку `r_useful=1` на отложенной выборке и не объявляются статистически
стабильными. Их цель состоит в проверке гипотезы, что представление ранга 1
устойчиво, но недостаточно различает экспертов при подборе пар. На проверочной
выборке выбирается один ранг для каждой пары `method` и
`compression_fraction`, после чего только победитель допускается к контрольной
выборке.

Поле `pilot.hybrid_pairing.variants` поддерживает именованные наборы весов для
следующего запуска. В проверке ранга оно намеренно не задано: сначала выбирается
ранг, затем отдельным экспериментом сравниваются веса без полного декартова
произведения параметров.

## Результат проверки спектрального ранга

Проверка ранга завершена полностью, но критерий перехода к нескольким слоям не
выполнен. Выбор ранга по одной проверочной выборке не перенесся на контрольную:
из четырех точек, где были выбраны ранги 4 или 8, улучшилась только одна на
0.16 п.п. Чистый RMT остался хуже простых базовых методов, а `usage_prune`
доминирует во всех трех долях
сжатия. Подробные результаты приведены в документе
`docs/8. Результаты usage-guided merge и rank ablation.md`.

## Следующий критерий перехода

Перед запуском трех репрезентативных слоев требуется:

1. выбирать ранг по нескольким фиксированным проверочным срезам и учитывать
   среднюю деградацию вместе с ее разбросом;
2. провести отдельную абляцию `hybrid_pairing.variants` после фиксации ранга;
3. сравнить равновесное слияние и слияние с весами по частоте использования
   (`usage-weighted merge`) при одинаковых исходных экспертах;
4. показать, что RMT-содержащий метод устойчиво не хуже `functional_cosine` и
   `random_merge` на 10%, 25% и 40%.

Только после этого запускаются репрезентативные слои и добавляются:

1. повторная загрузка материализованной контрольной точки для корректного
   измерения пикового потребления памяти;
2. многослойный контроллер `keep/prune/merge/abstain`;
3. смещение маршрутизатора H2;
4. динамический выбор `k` в H3;
5. профилирование с учетом межустройственного обмена.

## Многосрезовая проверка спектрального ранга

Следующий ограниченный эксперимент задается конфигурацией
`configs/experiments/h1_rmt_multislice_rank_validation_one_layer_pilot.json`.
Он переиспользует существующие трассы и H1-артефакты только для чтения, а
новые записи сохраняет в
`artifacts/h1_rmt_multislice_rank_validation_one_layer_pilot`.

Проверочные пакеты детерминированно распределяются между тремя срезами по
круговой схеме. Срезы не пересекаются, вместе покрывают весь оцениваемый набор
и отличаются по числу пакетов не более чем на один. Для каждого кандидата
вычисляются деградации perplexity `d_1, ..., d_k`, после чего используется
устойчивая оценка:

`robust_score = mean(d_1, ..., d_k) + std_penalty * std(d_1, ..., d_k)`.

В первой конфигурации `std_penalty=1.0`. Кандидат исключается из отбора, если
его общая деградация, `robust_score` или деградация хотя бы на одном срезе
превышает 5%. Среди оставшихся кандидатов для каждой пары
`method` и `compression_fraction` выбирается минимальный `robust_score`.

Результаты сохраняются в двух уровнях:

- `validation_slices` содержит метрики и деградацию каждого среза;
- `validation_robustness` содержит среднее, стандартное отклонение, худшую
  деградацию, `robust_score` и результат проверки жесткого ограничения.

При отсутствии `pilot.validation_selection` используется один срез и прежний
алгоритм отбора. Хеши старых конфигураций при этом не изменяются.

Пропускная способность на проверочной выборке включает отдельную синхронизацию
для каждого среза, поэтому служит только диагностикой этого запуска. Сравнивать
ее с одноразовой оценкой прежних экспериментов нельзя. Контрольная оценка
выполняется прежним способом без разбиения на срезы.

Ограниченный порядок запуска:

```bash
CONFIG=configs/experiments/h1_rmt_multislice_rank_validation_one_layer_pilot.json

.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step status
.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step baseline_validation

# Повторять ограниченными пакетами до remaining_items=0.
timeout --signal=TERM --kill-after=60s 45m \
  .venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" \
  --step validate_candidates --max-items 2 --max-step-seconds 1200

.venv/bin/python -m moe_opt_runner.pilot_cli --config "$CONFIG" --step select_candidates
```

Перед обращением к контрольной выборке следует проверить, что выбранные ранги
не определяются одним аномальным срезом и проходят жесткое ограничение во всех
трех срезах. После этого выполняются `baseline_test`, ограниченные вызовы
`test_selected` и `build_summary` по прежнему протоколу.
